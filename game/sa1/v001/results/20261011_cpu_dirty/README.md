# 転送範囲計算を本体CPUへ移す試験

同じ素材・物量・通常クロックで800フィールドを実行した。いずれも60fps未達。公開ROMは変更していない。

| 分担 | ロジック / 表示 | 画素一致 | 表示の2フィールド間隔 | 最大SA-1時間 |
|---|---:|---:|---:|---:|
| 全範囲を本体CPUへ | 579 / 576 | 167 | 70（3フィールドも1回） | 16.475ms |
| 小さい物を本体CPU、大きい物をSA-1へ | 605 / 602 | 168 | 46 | 20.134ms |
| 縮小パターン検索だけ本体CPUへ | 645 / 634 | 168 | 14 | 20.937ms |

比較元のBW配置表版は645表示・2フィールド間隔4回。上記は全て悪化した。全範囲版の最大SA-1時間は減るが、本体CPUのゲーム処理に加え範囲計算の最大約12.26msが必要になる。小さい物のみの分担でも本体CPUの空き時間を超える。表示枚数には起動準備時間の差も入るので、800で割ってfpsとはしない。

各画面を元のスプライトpacketから独立合成して全画素比較し、転送後のVRAMと実PPUの参照位置も確認した。同一世代のpacketは固定配置版と一致する。全範囲版の167枚は、最終表示世代の違いによる定期キャプチャ数の違いで、保存した画面は全て一致する。

`--cpu-dirty` が全範囲版、追加の `--cpu-dirty-small` が大小分担、追加の `--cpu-dirty-shapes` が検索のみ。再現コマンド・ROM SHA・詳細時間・検証結果はcommands.jsonとcomparison.json、画面・VRAM・計測ログはevidence.zipへ保存した。

本体CPUのDPは7E0400、作業域は7EF000から320byte。次画面の計算をSA-1の前画面描画に重ね、次のsubmitでBW432C00へ移す。SA-1が取り込むmask96byte、帯の範囲96byte、縮小パターンpointer128byteを使う。COLORBSSとの非重複をリンク後に検査する。大小分担では大きい物の範囲だけSA-1で加算し、検索のみ版は従来の範囲計算を維持する。

初期の二試作と検索のみ初版は速度比較から除外した。初期版はrow-dirtyのassembler define不足、次版は検索表のstrideを旧7byteと誤認（現在は10byte）して描画コードを誤参照した。検索のみ初版は既存plannerによるpointer書戻しへ保存値を渡していなかった。修正後の三件だけを上表と証拠に含める。
