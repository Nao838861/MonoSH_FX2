# 保持数・先行表示・DMA開始の追加比較

全件800フィールド、168画面の画素一致と実PPU参照位置・非表示期間の転送を検証した。60fps維持は未達で、公開ROMは4b39e4dの版を維持する。

| 試作 | 表示枚数 | 2フィールド間隔 |
|---|---:|---:|
| metadata保持数12、固定配置 | 647 | 4 |
| metadata保持数12、四面CHR、三枚を先行保持 | 644 | 6 |
| metadata保持数12、各面に配置表、三枚を先行保持 | 643 | 6 |
| 固定配置、16bit DMA開始 | 647 | 4 |
| 三枚先行保持、16bit DMA開始、転送余裕短縮 | 643 | 7 |

保持数を増やしても転送量の山は吸収できなかった。四面CHRでは配置表を表示時に読むため、元のBW面の再利用を表示後まで遅らせた。先行保持の起動時には最初の転送後にraw七面のprefillを再要求しないよう修正した。各面に配置表を持つ構成にも累積費用表を追加し、CPUコードの容量確保のため投影表を既存の未使用ROM領域へ移せるようにした。

16bit DMA開始は展開ブロックの間だけD=$4200、Y=$FE01とし、STY $0BでDMA開始と既存HDMA enable値の維持を行う。Dは呼出元へ戻る前に0へ戻す。記述子あたりの幅切替を省けるが、表示間隔は改善しなかった。公開版へは未採用。

`commands.json` に再現コマンド、`comparison.json` に集計と除外した失敗試作、`evidence.zip` に採取画面・実PPU状態・記録・最後の試作ROMを保存した。

`tile_cache_analysis.json` は公開版の負荷集中期間41画面から得た楽観的LRUの試算。512タイル保持でも新しいタイルが約95%を占める。表示中・待機中のタイル保護、ハッシュ、コピー、DMA開始の費用を含まないため、キャッシュ方式の速度実測には使わない。

`vram_fifo_capacity.json` は可変長VRAM保持の容量だけを調べた試算。固定配置版の静的素材を避けるBC20未満へ詰め、BG1の32KiB参照窓を越える場合は末尾を空けて先頭へ戻る。採取済み41画面の全サイズと1505通りの開始位置でタイル参照範囲を確認した。軽い場面は8～9枚、ピーク付近は表示中を含め4枚程度が入る。描画・配置表の保存／付替え・実DMAの時間は含めず、60fpsの証拠にはしない。実装は次の検証対象。
