# 不透明spanとnative行分割の検証

60fps維持は未達。今回は遮蔽方式を選ぶための独立したSA-1描画probeであり、遊べる統合ROMや実PPU表示の合格ではない。元の画像・paletteは変更していない。ゲーム側のbuildは逆順native v5、配布ROMも変更しない。

## 道中41画面の遮蔽量

配布固定map版から採取済みの世代530..570を使用した。元画像のalphaから同じQ8.8縮小・反転を行い、手前の爆発39/40/41（幅64以上）の各行で最長の不透明区間を選ぶ。区間内が全て不透明であることを検査する。奥のnative wordの4画素全てがこの区間に収まる場合だけ省く。wordの位相はspriteのleft byteを基準にする。

|方式|省けるword数|補足|
|---|---:|---|
|全画素の理想的な遮蔽|21,292|従来probeの上限|
|1区間/行・複数の手前spriteの合併|13,840|判定・生成費用を除く|
|1区間/行・手前spriteを1つ選ぶ|13,686|全有効126,381wordの約10.83%|
|2区間/行・手前spriteを1つ選ぶ|13,847|上積みが小さい|
|1区間/行・行全体を省く|1,269|118行・29連続区間、約1.00%|
|既存の左右端helper対象だけ|0|画面内の爆発が中心|
|右端helperを幅76まで広げる|603|約0.48%に限られる|

矩形の重なり面積が最大の手前spriteを選ぶ簡単な方法でも、この41画面では最良の選択と同じ13,686wordになった。一般の全場面で最良になることは証明していない。選んだwordを削って元の順序で再合成し、全最終sprite画素の一致も検証した。

現在のnative命令順で先頭に連続する隠れたwordに限定すると13,465wordある。左右の向きをspriteごとに選ぶ楽観的方式でも、この標本では同数だった。この数は途中のSTAが必要とするAの初期値や実行費用をまだ考慮しない。

## 容量と命令の正しさ

幅64以上の全対象76寸法では、不透明区間の生データが9,558bytes、行RLEは10,527bytesで大きくなる。後方の爆発39/40/41・幅49..79の5,665kernelに対する分割境界は46,452bytes、圧縮しても24,675bytes。選択表・pointer・行recordの費用は別に必要で、区間表だけを見て容量が足りると判断しない。

実ゲームROMの8,096行・5,665kernelから77,421境界を検証した。Aを`(old[offset] & mask) | constant`として扱い、入力FBの色を限定せずprefix/suffixの書込結果を照合する。繰り返しSTAから再開する13,663境界も初期Aを確認した。元コードには他wordの入力へ依存する命令がないことも検査する。prefixとsuffixの任意の組合せ597,916区間に相当する分割が成り立つ。これは静的検証で、実機速度の測定ではない。

## SA-1での描画時間

108通りの2爆発fixtureと上記41 packetを、実SA-1がROMの65816命令を実行してBW-RAMへ描く。通常描画、DMAでprefixをI-RAMへコピーする分割、MVNコピーの分割、コピーなしの直接再開を比較した。全596出力FBが独立した元画像合成と一致した。

通常描画と各方式で、隠れない連続行はnative call chainへまとめる。遅い1行ずつのdescriptor解釈を通常描画に残した比較では、小さな見かけの改善があったが、これを最終判断に用いない。

|描画時間の合計|通常描画|DMA分割|MVN分割|直接再開|
|---|---:|---:|---:|---:|
|2爆発108例|234.832ms|261.085ms|266.682ms|165.846ms|
|道中41 packet|174.956ms|196.160ms|196.439ms|160.787ms|

DMA/MVN分割はどちらの集団でも速いケースがなく、道中では合計約12.1%/12.3%悪化。prefixのコピー、descriptor読取、呼出の費用が削減量を上回る。この方式はゲームへ組み込まない。

直接再開版はnativeの先頭の隠れた命令だけを省き、最初に残る命令がSTAなら直前のLDA即値またはLDA abs,X（opcode BD）まで戻して、Aを外から設定せずに再開する。戻した分の隠れたwordは描いて構わない。内部区間だけが隠れる行は元のまま描き、全行が隠れる場合はcall自体を省く。道中で実際に省くwordは12,535、通常描画より速い25画面、同じ16画面、悪化なし。合計約8.10%、最良約19.85%短縮した。

ただし直接再開版は、遮蔽候補の選択・区間検索・境界検索・call chainの形成をホストで済ませてROMへ事前保持した楽観的な計測。viewport clippingも事前計算する。通常ゲームのIRQ、物理処理、音、背景描画、変換・PPU転送はこのprobeへ統合していない。ゲームの描画時間が8.1%短くなる、あるいは60fpsになるという結果ではない。次は安全なLDA/BD再開位置のhintと既存11byte行call chainのpointer更新を実装し、その費用を含めて測る必要がある。

## 計測の訂正と再現

初回probeにはDMA clearの起動レジスタ順序の誤りがあり、FB不一致になった。修正後の一時版では開始callbackが行loopの先頭と重なり最後の1行だけを計測していた。コメンタリの「全ケースで遅い」はこの時点では根拠が不適切だったので訂正した。開始点をloopから分離し、各jobでcallbackが1回だけであることを検査した。最終判断はこの修正とnative chainの比較を反映した596画面の結果だけによる。失敗ログ・誤った集計は証拠zipのexcludedへ分ける。

commands.jsonで再現できる。Windows標準のPython3.10ではなく、bundled Python3.12を使用する。comparison.jsonはSHAと集団別の値、feasibility.jsonは全41画面の遮蔽内訳、capacity.jsonとfragments_verified.jsonは静的検査を保存する。evidence.zipには計測ROM・labels・命令/入力表・全596FB・実行ログ・元packet/FB82ファイル・基準ゲームROMを収録する。基準ROM SHAは7124eab2f29ffca6904f68d1c7ee705933dd0b341bbb0082db9366468fc4a7fb、配布ROMは9934d77b85913187be8d3ebd8315f854718eb24b08492204ce8b3288f620146cのまま。
