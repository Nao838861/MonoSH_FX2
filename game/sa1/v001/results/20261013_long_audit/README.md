# 長時間監査と、狭い右端の部分描画

60fpsは未達。通常クロック・全44素材・1492寸法・色・物量・ゲーム処理を保持した独立SA-1分岐で比較した。公開ROM9934d77bは変更せず、作業用の既定ROMもa9bcd247へ戻した。試作は既定OFF。

通常プレイを無敵化せず4000フィールドまで実行すると、短い試験では見えていなかった道中後半が重い。基準f685de70の最大SA-1時間は25.373241ms、内訳は描画20.906752ms・dirty計画2.737778ms・消去1.427276ms・背景0.301435ms。ゲーム処理は別CPUと重なるため、logicMsをこの合計へ再加算しない。

表示間隔は起動後の最初の2枚を除いて数える。起動待ちを含む4000field全体の平均だけで60fpsと判定しない。v1/v2とも共通3826世代のpacket・全256×192 packed framebufferが基準と一致し、3827世代のtile maskと消去端も一致した。通常プレイではlogic3362で死亡中、3459で地上の死亡状態、3567で復帰、3695でボス戦へ移行。3版の共通3826完了更新のゲーム状態も一致した。死亡時にもruntime frameはリセットしない。

右端にわずかに見える草木では、画面外を含むnative描画と退避・復元が大きい。新経路はROM内でhelperを実行し、元のnative行を先頭から調べ、見えるprefixだけ0500のIRAMへコピーしてRTLを付ける。右端のword書込みが次行へ触れる1byteを保存・復元する。従来のhelper全体のIRAMロードは行わない。`--right-narrow-prefix` がv1、さらに `--right-narrow-scenery` がv2。

v1は669物体・15362行を通ったが、背の高い木4では行単位の処理が増え、対象を広げるほど速いとは限らない。v2は131物体・1389行、実行した素材は0/2/3、コピーしたprefixは最大24B。v1で測った同一物体のうち、v2候補113件の平均短縮は0.738msだったが、これは全フレームの改善量ではない。全体の表示待ちは28→24回で、毎フィールド更新には達しない。

ボス試験は開始条件とstage frameを注入し、無敵化する。通常クリアとは区別する。基準4000fieldは表示3843・1:3833/2:7・最大20.562295ms・182画面一致。v1/v2は5000fieldでどちらも表示4834・1:4815/2:16・198画面一致。最初の4000fieldに限ると両方1:3831/2:8で、改善していない。共通3848世代の全framebuffer・ゲーム状態は基準と一致。HP0、boss state 2/3、stageへの復帰と注入による再度のボス移行まで記録した。最大時間22.340919/22.449499msは5000field全体であり、基準4000fieldの最大と同じ区間ではない。v2はボス試験中に新helperを通っておらず、ボスの数値差を部分描画の効果と扱わない。

静的検証は各試作ROMの56172 native kernel・755232右byte境界で、全行実行とprefix実行を照合した。入力下地を記号的なmask/valueとしても評価し、任意の下地で可視bitが同じことを確認。実機のSA-1を使った測定は未実施で、Mesenの通常クロックでの結果である。

監査callbackはゲーム状態を書き換えない。boot内の最初の更新は外側のlogic_finishedを通らず、field終了時には最後の更新が実行途中のことがある。初回host検証の「1から全件完了」という仮定が失敗した。起動1件と終了時未完了0〜1件を明記し、途中の欠落は許容しない形へ修正した。基準の同じ保存データを再検証し、初回host失敗の記録と再検証結果をroad_base.zipへ残した。エミュレータ障害として隠していない。

## 資源案の確認

草の9行目をBG2へ移してVRAMを空ける案は導入しない。元画像512pxには透明画素が12個あり、256px周期ではなく反転で共有している。相対scroll512通りを調べると、nearが62→32 tileになってもfar側が最大96 tileへ増え、CHRは最大64B増加する。約1KB空くという初期見込みは誤りだった。near_row8_capacity.jsonは元画像による容量計算で、ゲーム統合や速度の証拠ではない。

次の候補は、背の高い木4のnative行を逆順にし、右端の可視部分へ直接入る方法。76寸法・9336行・5751 kernelを数え、同じmask/valueになる逆順コードを作る容量probeを保存した。コードは14481B増、共通圧縮hintは211種類・1349B。各kernelに3byte pointerを足すと33083B増だが、1byte hint番号と共通pointer表なら算術上22214B増。実際のbank割付、他素材と共有する旧kernel、通常描画・左clip・dirty bandのfallbackは未解決で、実装済み・高速化済みとは扱わない。

commands.jsonに再現コマンド、comparison.jsonに集計・SHA・zip一覧を保存。各caseのzipは全計測ログ・packet・全世代framebuffer・VRAM・PPU・palette・RGBを含む。roms_and_sources.zipは3版のROM/labels/map、生成source、静的証拠、host再検証script、容量probe入力、既定復元smokeを含む。PNGはRGBと重複するため省略。既定復元後の280fieldは表示131・120画面一致・最大7.241609ms。これは軽い区間の回帰確認で、全編60fpsの証拠ではない。
