# 最新の敵弾描画とVRAM四面の再試験

敵弾の透明形状共有・ROM直接実行・no-history・bullet-residentを、以前は単独で遅かったVRAM四面へ組み合わせ直した。**この測定の固定map・四面は実際のPPU参照位置に不整合があり、正常表示の検証としては無効。60fps未達。f8dbe7cの試遊ROMも修正版へ差し替える必要がある。**

| 方式 | fields | 表示枚数 | 画素一致 |
|---|---:|---:|---:|
| 現行固定map二面 | 800 | 644 | 168 |
| VRAM四面＋最新描画 | 800 | 644 | 168 |
| 四面＋flip予約量調整 | 800 | 644 | 168 |
| 四面＋本体CPUで生成した費用表 | 800 | 641 | 168 |
| 四面＋SA-1で生成した費用表 | 800 | 644 | 168 |
| 四面＋費用表の分割済み先頭量補正 | 800 | 644 | 168 |
| 最新描画＋表示中のWRAMへの先行変換＋VRAM三面 | 800 | 631 | 168 |

入力をlogic世代へ固定し、描画packetも同世代で一致する。ただし表の「画素一致」は、検証器が仮定したVRAM配置での復号結果である。PPUが実際に参照するCHR・配置表の開始位置を確認していなかったため、表示画面の一致は証明しない。

四面では通常、表示待ち画像を3枚まで先行できる。しかし重い爆発区間で転送待ちが溜まり、先行分を使い切った。通常のflip予約を4200→3600、自機画像更新時を4300→4700 unitsに調整しても枚数は変わらなかった。この短区間だけで予約量の安全性を一般化しない。

部分転送の線形選択は最大約1.6ms。累積費用表の二分探索では約0.3msへ減ったが、本体CPUでの表生成がゲーム側を重くした。SA-1表でも総表示枚数は改善しない。四面と費用表を組み合わせる際は、収集前には末尾map記述子が存在し、plan時には除去済みである点を分ける。plan側で記述子数を余分に1減らさない。

`--prefix-table-partial` は先頭の記述子が途中まで送られていた場合、元の累積表から転送済みbyte数と費用を差し引く。この試験の枚数には寄与しなかった。IRQで本体の除算器を使わず、既存のROM表で記述子番号を求める。

最後のWRAM先行変換も、以前の試作を最新の敵弾形状共有へ接続し直した比較である。待機中消去と281行期限も接続した。表示中にSA-1の文字変換DMAで連続CHRをWRAMへ作り、非表示期間にはまとめて送るが、生成と転送の待機が重なり表示枚数は減った。

7試験・6組のROM/ラベル/manifestを`evidence.zip`へ保存する。非表示期間のDMA開始・終了は確認したが、正常表示の検証としては採用しない。固定mapは2KiBの配置表整列、遠景は8KiBのCHR整列に違反していた。四面はCHR開始位置の計算と12KiBページの奇数面に必要なタイル番号補正が誤っていた。実際のPPU状態を記録・照合する検査を追加し、修正版で別に再試験する。
