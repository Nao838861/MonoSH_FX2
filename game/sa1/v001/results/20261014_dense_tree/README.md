# 木4のPEA/PHA描画を実ゲームで比較

60fps未達。この版は画素検査に合格したが、通常プレイの表示待ちが増えたため不採用。既定a9bcd247と公開9934d77bを保持する。素材・縮小寸法・色・物量・通常クロックを変えていない。

木4の全76寸法を、不透明wordはPEA、部分透明はLDA/AND/OR/PHA、内部の完全透明wordはLDA/PHAで保存する連続した降順コードへ置き換えた。SをBW-RAMの8KiB窓へ移し、行の終わりにJMLでIRAM0700の復帰gateへ戻す。通常Sへ戻してからIRQを許可する。画面内と右端はROMコードを直接呼び、左端は可視prefixだけをIRAM0500へコピーして物体内で再利用する。最大コード97Bで、05C0のCC1作業域に重ならない。

## 境界不具合と修正

初回40094cd2は通常800field・648表示・128実PPU画面の画素検査に合格したが、全寸法の境界試験でpresent00013の1byteが欠けた。4×9の木を中心0と256、bottom209に置いた画面で、framebuffer offset23552（y184、x0の2画素）が期待132に対し0だった。

左端の部分wordが8KiB窓の境界にある場合、low byteは画面外でもhigh byteが最初の可視byteになる。low側の窓へSを設定すると、S8000のhigh byteがROMへの書込として無視される。左clipではhigh側の窓を選びS6000から書くよう修正した。右clipはhigh byteが画面外なので、low側の窓を使う。guardの保存・復元も維持する。

修正版c33bdcafでは、全5751kernel・9336行使用を元のnativeコードと独立に照合した。左右の全byte境界（右90588・左84838）と任意下地のmask/valueが一致。さらに複数の8KiB境界・raw開始位置を含む569088可視byteの窓割当を独立に照合した。全素材1492寸法・90854 native行使用・158688弾行使用、5992 dirty縦位相も検査した。

実行中には、16bitレジスタとIRQ禁止状態、Sの範囲、実コードのpush回数と復帰時S、IRAMへコピーしたprefixの全byteとJML復帰先、端のguard復元を検査した。全76寸法×左右12位置×上下3位置の2736ケース、1369実PPU画面が一致した。初回不具合のROM・source・capture・期待画像は別の失敗資料として保存し、速度合格へ混ぜない。

修正版の境界fixtureも1520fieldで1369表示、1:1365/2:1。前段では定常1366区間が毎fieldだった。限定fixtureでも全体ゲームでも速度改善と判定できない。

通常プレイでは、左端で個別に短縮する例がある一方、画面内の木が大幅に遅くなる。共通job/indexの例では54×126の左端の木が約3.732ms短縮したが、画面内68×158の木は2.589→8.035ms、66×152は2.443→7.485ms。これは共有バス・IRQを含む物体観測時間であり、命令固有の一定短縮率とは扱わない。通常Sへの復帰、窓設定、行のheader/hintと行ごとの準備処理を増やした費用が大きい。PEAの命令数だけで全体の高速化を判断してはいけない。

comparison.jsonに全世代framebuffer・packet・tile mask・消去端・ゲーム状態の基準比較と集計、commands.jsonに再現手順を保存する。dense_tree_v2_buildには独立したopcode検査と全素材検査の結果を保存。case zipにはRGB・実PPU/VRAM・Lua・状態と計測、roms_sources.zipには初回/修正版ROM・labels・source・ビルドログを保存し、各zipのSHAとCRCを検査する。

## 次に調べる点

一行ずつ重い準備を行う方式は避け、既存の複数行call chainを保ったまま、画素を書き込む命令とROM読出しを減らす構成を調べる。DPをBW-RAM窓の描画先へ置き、LDA/STAの短いdirect-page命令を使う案がある。kernel末尾でD=0へ戻せば、従来の11B行chainのTAXをTCDへ置換できる可能性がある。窓の境界を跨ぐ前にchunkを区切り、edge保存・復元の前後ではrawのspriteBaseを保持する必要がある。既存のclip JIT/hintは3B命令を前提にするので、そのまま流用できない。

IRQ handlerはPHD、D=0、PLDでDを保持していることを確認済み。ここまでではDP案は未実装・未計測で、速度改善とは扱わない。前段の表示入口/出口分類では23待ちのうち18回で非表示開始時にready=0・rendering=1、5回では転送対象が残っていた。描画と転送の両方の締切を検証し続ける。
