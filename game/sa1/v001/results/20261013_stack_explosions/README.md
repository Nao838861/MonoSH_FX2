既存の全1,492寸法と素材を維持し、爆発40/41の幅94へ逆順PEA/PHAによる描画コードを追加した。最大8行ずつBW-RAMのmapとstackを切り替え、行末にJMLで戻る。ゲームへ統合した通常クロックの実測では60fps未達。公開ROMは変更していない。

全件で実PPUの参照先と転送済みVRAMを確認し、元packetの独立合成と全画素一致。同一世代packetは固定配置版と一致した。800で表示数を割ってfpsとはしない。比較元のBW配置表版は645表示・2フィールド間隔4回なので、これだけでは全体性能を改善しない。特定の爆発を速くしても、非対象寸法の描画と準備・転送が残る。

幅94の二素材・高さ73/74・横位置の偶奇に対応し、330行recordを共有して実データ30,712バイトで保持した。追加領域はDF7020..DF7FFF、DF9200..DFBFFF、FEC400..FEFFFF。DF8000..DF91FFには既存近景データがあるため使わない。元データが全零であることを配置前に検査する。helperは03E400へ置き、既存地面コードとflip領域、零sourceを避ける。

元native行と生成したstack行は330 kernel・11,696右端byte境界で一致。実機構成の境界fixtureは、横13位置、上端・中段・下端の7位置、高さ2種類を循環する。v4の500フィールドは347表示すべて一致、末尾停止0。圧縮併用版も同じ347表示が一致。草・木の左端fixture320フィールドは170表示・保存120画面が一致した。これらの限定fixtureで毎フィールド表示できても、ゲーム全体の60fps達成とは扱わない。

## 停止の原因と修正

v2/v3の境界fixtureは172表示の後に停止したため不合格。保存した172画面の一致だけで通過させない。SA-1のPCが0500の零命令からBRKへ進む記録を取得した。新しいstack描画を外した比較ROMでも同じ種類の破損を再現した。

既存のedge_cached_game.sで `top + sourceFirst + rowCount` を計算するとき、負のtopとsourceFirstの加算で発生したcarryを次の加算へ持ち越していた。退避行数が1行増え、幅28byte・chunk16行では本来18行=504byteのところ19行=532byteとなり、0300..04FFを超えて0500のJITを上書きする。rowCountを加える前にCLCを追加した。幅24byteでも最初の長いchunkで同じ破損が起きる。失敗fixtureとPC記録はevidence.zipのfailedへ保存した。

## 容量を取り戻す圧縮

`--left-hints-compressed` は8境界ごとの基準値と2bit差分を保持する。差分は0/1/2/4のみ。短い表は従来形式を残す。SA-1は256byteの和テーブルで復号する。全4,998 kernel・77,751境界をROM内のnative命令から求めた開始位置と照合し、全内容を維持して50,079→25,514byte、24,565byte削減。ROM末尾のbankを避ける配置の丸めも減り、payloadEndは7EC39Fから7DB3A7へ移った。速度向上ではなく追加の高速描画コードを置く容量の確保が目的。

現行ソースの再現はcommands.jsonのv4または圧縮版を使う。v1..v3はCLC修正前の履歴測定で、同じコマンドを現行ソースで実行したROMとはSHAが異なる。各測定の実ROM・label・map・manifest、画面・VRAM・packet・計測ログはevidence.zipへ固定した。詳細はcomparison.json。次は圧縮で空いた領域へ、現在最も重い幅91などの爆発のコードを追加して再測定する。
