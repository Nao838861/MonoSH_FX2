## 保存VRAMの解析

`python tools/analyze_sa1_map_transfer.py movestress_directsparse3_opacity_long_tracepalette` は実VRAMから各ページのマップを読む。先頭120世代は全て捕捉され、高byteが全て24のままなので、低byte736Bだけの送信なら736Bを省ける。動的tile IDが256以上の箇所だけ高byteは25になる。

重い保存画面では高byte25の範囲は最大398B。後半の捕捉は60世代ごとのため、同じページの直前状態は不明として削減量を計算しない。新旧ページの高byte範囲の和を更新する実装と、画素比較による確認はまだ行っていない。削減したDMA時間に対し、SA-1でマップを分離する計算費用が増えるので、全体速度を実測する必要がある。

実装候補は、マップ生成時から低byte736Bと高byte736Bを別の連続領域へ書き、2115の増分条件と2118/2119を切り替えて送る方式。高byteが以前25だった領域を24へ戻す処理、3ページ別の履歴、CHR部分転送後の再開、実際の転送量による締切判定が必要になる。ゼロ長DMAは発行しない。

別候補として、12KBのCHR領域を4面にし、各面末尾の2KBへマップを置く配置も検討した。マップ末尾の非表示8行をCHRへ再利用すれば1面335動的tile程度となり、実測の道中最大325tileを上回る。ただし全場面の上限と、地面・遠景・OBJを残り16KBへ再配置できるかは未検証で、未実装。現在の三面を置き換えたものではない。
