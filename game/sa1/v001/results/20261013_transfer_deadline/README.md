# 転送期限の追跡と予算計算の一本化

60fpsは未達。独立SA-1分岐で、元の4bpp素材・全縮小パターン・物量・ゲーム時計・通常クロックを保持したまま測定した。公開ROMは更新しない。

## 待ちが起きている場所

基準は前回のlarge12版（SHA `24bac324...`）。道中の表示待ちでは、SA-1の完成画像がキューに3～4枚残り、転送完了画像が0枚だった。描画待ちだけでは説明できない。

197行IRQ、転送先選択、CC1設定、全量の費用計算、時刻取得、部分転送の費用計算、再度の時刻取得、探索を順に実行していた。世代543では基準のfast開始が207行、実際の最初のDMAが208行付近になり、翌フィールドの6行目で部分転送が終わっても1440byteが残った。次のIRQへ持ち越している。

`--trace-transfer-deadline`は命令列を変えず、660～720フィールドのIRQ・準備・予算・部分転送・DMA開始・完了・切替を記録する。DMA開始時の転送量・送信元・実PPU VRAMアドレスも保存する。最初のbaseログだけは送信先をwrite-onlyレジスタから読んでいたため、その項目をアドレス検証に使わない。以後はPPU状態から読む。`pipe_reserved`時点のavailableは保存前の値であり、新しい予算はAにある。

## 試した変更

- `--prefix-unrolled-search`：最大48記述子の累積費用表を、32/16/8/4/2/1の6段探索に展開。境界と厳密な`cost < limit`を保ち、Yを復元する。基準と同じ転送量を選ぶ。探索単体では待ちを減らせなかった。
- `--dma-budget-table`：走査線から残り時間を求める乗算をROM表へ置換。表示範囲・締切・切替の余裕を保持する。
- `--prefix-one-pass`：累積費用表で全量／途中転送をまとめて選び、時刻取得を一回にする。全量が収まる場合は探索も省く。途中分割済み記述子のbyte数と費用を差し引き、全量を選んだ場合は従来の完了処理へ進む。
- `--prefix-full-reserve 192`：全量が収まる場合だけ、計画処理の余裕を384→192byte相当へ変更。部分転送の余裕384、表示切替2200/2300、先行転送900は維持する。世代546の最後の128byteを除外していた場面を調べて追加した比較であり、通常設定には採用していない。

一本化版は既存の`--dma-word-start`も組み合わせている。その効果を単独測定したとは主張しない。SA-1の描画命令は変更していない。SA-1時間の差にはS-CPU・DMAとの競合と進行位相の差が含まれる。

## 境界・再開・元画像の検査

実ROMの探索命令を独立の最小65816インタープリタで59024条件、全量判定の入口からも58148条件実行。0～48記述子、費用境界の直前／一致／直後、複数の初期位置を試す。全量判定は実際の費用上限内で検証する。人工的な65535への余裕加算は実行範囲と区別した。予算表は512走査線×512水平位置、262144条件を旧式と比較した。

実行時も各fast転送の直前に累積費用表を線形走査し、選んだ記述子数とbyte数が正しいことを検査する。元の記述子長から途中分割済みの長さを求めて照合する。

専用fixtureでは元の爆発40/41を94×74のまま9個描き、途中分割と次のIRQからの再開を通した。384版・192版は各500フィールド・142画面すべて照合に合格。384版では467回の転送選択のうち168回が途中分割済み記述子からの再開、最大2848byte分割済み、最大27記述子。192版は465回中169回、最大2816byte。fixtureの更新間隔は2～3フィールドであり、ゲームの60fps達成には数えない。500フィールドで終了した時点の末尾待ちは、この試験の通常の2～3フィールド間隔内である。

全1492寸法、native90854行、弾158688行が基準ROMと一致。元画像alphaから独立に再計算した5992縦位相のdirty範囲表も一致した。ホストは検証とfixtureのpacket配置だけを行い、SA-1の描画を代行していない。

## 不採用の途中結果

最初の予算表では末尾の`.segment "GSU"`からCODEへ戻していなかった。後続の`blank_table`までGSUへ移り、HDMAがWRAM内の別データを表として読む配置になっていた。組み合わせ版SHA `d4250fce...`の道中・fixtureが画素照合を通ったことだけでは正常性を認めない。最初の一本化SHA `6f5372f6...`ではfield145/line203に値35で予約期間をunblankし、検査が停止した。これらを性能の証拠から除外する。

予算表末尾で明示的にCODEへ戻し、`blank_table`をexportしてCODE範囲内であることをbuild時にassertする。最終の静的検査とテスト起動前にも、ROM内の表13byteが正しくS-CPU CODEに存在することを確認する。修正版384のSHAは`b69e6e41...`、192は`f685de70...`。384版の再buildは同じSHAになった。

初回の静的検査器はC1のROM物理位置を誤り、ADC absolute／DECの未実装opcodeでも停止した。物理位置と命令を補ってから、実ROMに対する全条件を最初から実行し直した。未対応opcodeを無視して合格にはしない。最初の一本化の分岐距離超過も、long jumpへ修正してから実行している。

## 保存と次の検証

`commands.json`が再build用の引数列、`comparison.json`が集計結果、`evidence.zip`がROM・labels・map・生成source・Lua・転送ログ・画像照合用の全データ。`invalid_*`は不採用の診断資料で、採用結果と分離している。最初の不合格一本化ROM本体は上書き済みで保存されていないため、保存済みと主張しない。

証拠zipは42,304,565byte、SHA-256 `db5b34fe9fbe9491c8039bb6e8dafbbbb6a85e4ee02e5bec18e791651872d867`。ZIP CRC検査に合格した。検証時点のsourceを含むので、以後の説明文だけの修正と区別できる。

Pythonはbundled 3.12を使用し、各build後にMesenとホストの画素照合が端末で完了してから次のROMへ進む。通常buildをSHA `a9bcd247...`へ戻した。279フィールド・137logic・130表示のsmokeは120画面照合に合格し、最大7.241609ms。公開ROM SHA `9934d77b...`は維持した。結果は`default_restore.json`へ記録した。自前の試験Mesenとホスト検証は終了済み。

残る課題はVRAM二面の所有期間と転送持越し。次は、切替のためのWRAM状態準備を197～203行の間へ前倒しし、実PPU更新だけを非表示開始まで待たせられるかを確認する。過去の低余裕設定での表示行超過を繰り返さず、DMA完了・実PPU参照・画像一致で評価する。全ゲーム・全武器・敗北までの4000フィールド監査も未完了である。
