# VRAM面の適応更新とS-CPUソートの検証

60fps未達。公開ROMはe5e4741のまま。素材・物量・通常クロックを維持した。

|方式|実field数|表示枚数|FB/VRAM一致枚数|表示間隔field数:回数（初期2枚除外）|
|---|---:|---:|---:|---|
|adaptive|600|495|126|1:480, 2:12|
|bossadaptive|1200|1059|135|1:1009, 2:46, 3:1|
|bossradixverified|1200|1078|135|1:1045, 2:30|
|bosskeybuckets|1200|1035|135|1:959, 2:73|
|bosskeyranges|1200|1079|135|1:1047, 2:29|

比較元は`3312524`のpacket-shapes構成で、道中505枚・ボス1079枚。各JSONにはROM/labels SHAを記録する。

`--adaptive-vram`はVRAM各面の未反映の変更領域を独立に累積し、変更量が小さい時は表示面へ一括転送、大きい時は裏面へ分割転送する。CPUが実際に転送を完了した世代を低8bitのatomic値で公開する。SA-1は世代変更を観測すると直近4世代のdirty履歴から再構成し、それより古い時は全面更新へ戻す。BW43:6000以降を使い、既存の履歴43:04C0..051Fとの重複を避けた。画素は一致するが、二面分の履歴・descriptor管理と待ちが増え、最良方式より遅い。採用しない。

`--radix-sort`は奥行き、priorityの二段の安定bucketソート。最初の試作で表示1103枚を記録したが、これは順序検査で不一致が見つかり、性能の根拠から除外する。原因は前段・前フレームのbucket headが残り、今回未使用のpriorityへ混入したこと。走査時にheadを消す修正後、全ソートを独立した安定ソートと照合し、ボス1078枚となった。改善しない。

`--key-buckets`はpriority 0..2の全768キーを一段で処理する。7F:F800..FDFFを専用scratchにし、CODEがF800を越えないことをlinker assertする。起動後に専用領域を明示初期化する。大きな未使用キー範囲も走査する初版は1035枚で遅い。現行版はpriorityごとに実在する奥行き範囲だけを走査し、1079枚で比較元と同じ。priority範囲外は元の挿入ソートへ戻す。小さいpacketも元の処理を使う。採用しない。

順序検査をradix/key-bucketsへ拡張し、キー、元index、同一キーの安定性を全呼出しで確認する。FB/VRAMの画素照合は先頭120枚と以後60枚ごとの採取であり、全表示枚数を画素照合したとの意味ではない。

再現は従来の最良構成へ各flagを追加する。adaptiveはradix/key-bucketsを加えずに検証し、二種のソートも互いに併用しない。次は遠景のBG2化を別flagで検討する。遠景タイルは上下左右反転を共有すると64種類・2048B、地面は反転共有で399種類・6384B。地面の絵を変えずに1808B空けられるため、VRAM配置を工夫すれば遠景のnative BG化を試せる。
