# 直接4bpp描画の速度・容量試験

既存素材・55fixtureを使い、出力を直接SNESのplanar形式へ描く小さなSA-1 ROMを作った。全件で画素一致を確認した。比較のためpacked形式にも同じ固定位置のコンパイル試験を作った。

| 固定位置fixtureの描画方式 | 最大描画時間 | 全面消去込み |
|---|---:|---:|
| packed形式・完全コンパイル | 7.583ms | 12.171ms |
| planar形式・完全コンパイル | 8.440ms | 13.028ms |
| planar形式・1bitplaneずつ完全コンパイル | 11.813ms | 16.401ms |
| planar形式・辞書を参照 | 20.514ms | 25.102ms |

これは位置・寸法・反転が既知のfixtureをコンパイルした有利な条件であり、ゲームの実行時間や60fps達成の証拠ではない。縮小寸法検索、配置計算、キュー、PPU転送、ゲームロジックは含めない。packedもplanarも同じ条件で比較する。従来probeの一般的な行描画版と直接比を取って高速化としない。

ゲームで必要な全寸法・横8位相のデータ容量は、直接データ13,103,268bytes、全体辞書10,019,188bytes、素材別の密な辞書6,893,196bytes。最後の方式だけが8MiB未満になるが、ゲーム本体・実行部・元絵fallbackは含めていない。辞書参照版は描画だけで16.7msを超えた。

コードをplane単位で共有しても、2plane単位28,235,292bytes、1plane単位32,029,377bytesとなり、参照記述子を含める前からROM容量を超える。位置に依存しない行コードのRAMキャッシュも、固定配置版のpacketを世代順に処理した試算では、負荷集中41画面・13,522行呼出しに対して128KiBで9,936回のmiss、生成コード974,025bytes（最大36,041bytes/画面）。コンパイル時間やBW再配置を含まない楽観的試算でも再利用は少ない。

再現は `build_sa1_planar_probe.py` の `--packed-native` / `--native` / `--bitplanes` / オプションなしと、それぞれ直後の `test_sa1_probe.py`。全寸法の容量は `analyze_sa1_planar_data.py --native-planes`、行コードキャッシュは `analyze_sa1_planar_code_cache.py`。試験ROMは8MiBだが、収録しているのは55fixtureの固定位置プログラムで、全縮小コードが入るという意味ではない。

公開ゲームROMへは未採用。60fps維持は未達。
