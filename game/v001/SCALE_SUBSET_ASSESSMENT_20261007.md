# 縮小パターンをボスの一部へ限定できるか

2026年10月7日。**可能。最初の候補はボス胴・顔・弾の3素材だけを残す構成。** 今回は既存コードと保存済み計測を調べた検討であり、描画コード・生成画像・公開ROMは変更していない。60fps維持は候補構成での再計測前なので未確定。

## 追加画像の容量

現行は横方向だけのQ8.8変換行を4画素/byteで保持し、縦は実行時V/DVで選ぶ。幅ごとの必要量は `原画高さ × ceil(出力幅 / 4)`。

|ボス顔|14|84×128|1〜96|153,600|
|ボス弾|31|128×125|1〜96|150,000|

|構成|追加画像KiB|現行から回収するKiB|
|---|---:|---:|
|現行6素材|631.7|0|
|ボス胴・顔・弾のみ|397.3|234.4（37.1%削減）|

これは画像データの占有量。既存bankのpaddingを再利用しているため、限定しても現行のROMファイルは2MiBのまま。空き領域が増え、今後の素材を入れやすくなる。64KiBの索引は現行形式のまま維持する。

## 道中の根拠と残る確認

保存済みの最終版と`--no-scaled-rows`版の122標本比較から、実ゲーム由来かつボス胴・顔・弾を含まない69標本を抽出した。同じ場面を含む二つの入力記録であり、69場面のすべてが独立した状況という意味ではない。

- 縮小パターンありのGSU最大：11.363ms。
- 縮小パターン全部なしのGSU最大：11.085ms。
- なしにした時の時間増分：平均0.112ms、最大1.484ms。場面によっては逆に速くなる。

GSU時間は部分クリア・準備・描画・区間表作成を含む。最大値を取った場面は前後で異なる。さらに全無効版はGSUのcache配置やUV準備経路も変わるため、これを「草・木だけを除いた現行版」の正確な時間とは扱わない。CPUのOBJ/direct page、DMA区間表取得・生成cache、転送締切拡張の改善を残せることも、道中のパターンを撤去できそうな理由になる。

一方、現行の長時間ログには、GSUが約0.98ms余計にかかると締切へ近づく道中画像がある。これは現在の開始時刻・転送量・CPU終了・準備時間から計算した上限の目安で、再構成後の入力やDMA位相が同じとは限らない。69標本で最大1.484msの差もある以上、道中がほぼ60fpsだったことだけでは長時間の遅延0回まで確約できない。[容量・標本・余裕の算出結果](results/scale_subset_assessment_20261007/assessment.json)。

## 素材を減らす際の構造

現在の索引は`[asset*1024 + width*4]`で参照し、未収録幅のbank値0を見つけると従来の任意倍率描画へ戻る。特定素材の索引を0にしてそのパターンを生成しなければ、同じ構造でボス限定にできる。CPUのコマンド形式、clip、透明合成、描画順、縦方向の倍率、共通485byte cacheを変更する必要はない。

さらにボスの幅の一部だけを残すことも可能。抜けた幅は汎用描画で同じ画素を選ぶので、縮小の段階を荒くする必要はない。ただし大きい原画だけを基準に選ぶと、胴を8節描く累積費用や、接近した複数の弾を見落とす。素材ごとの「表示画素数×同時個数」で優先度を決めるべき。

以前の胴64px上限の試行では、撃破中を含むボスの最大GSU14.623ms・遅延2回があった。後のCPU/cache修正も入るため、上限だけの比較ではないが、撃破時の大きい胴を省いてよい根拠にはならない。現在の胴96px上限は最初の候補では残す。

## 推奨する検証順

1. CPU・GSU cache・DMAの最新最適化を保ち、ボス3素材だけ収録する候補を比較する。追加画像約234KiBを回収できる。
2. 道中とボス撃破・次周を含む通常入力、ボスを長く残す入力で提示間隔を測る。前回と同じ18,000fieldずつを基準にする。
3. 道中に遅延が出たら、その場面の大きい木など必要な幅だけ戻す。全1〜128幅を復活させる必要はない。
4. ボス3素材で余裕があれば、顔・弾のみ、または素材別の幅制限を検討する。胴8節と撃破中を含め、削除単位ごとの時間差を実測する。

判断：**道中の全縮小パターンを保持する必要性は薄く、ボス限定へ絞る余地が大きい。** まず3素材を残すのが、容量削減と60fps維持を両立しやすい候補。顔・弾の2素材まで減らせるかは、ボス胴の時間差を分離してから判断する。今回の検討では候補を実装していない。
